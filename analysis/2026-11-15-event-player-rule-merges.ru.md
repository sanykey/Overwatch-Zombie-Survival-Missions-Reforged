# Кандидаты объединения правил с Event Player

**Внедрение:** по запросу пользователя объединены только Ultimate resist + Apothecary и два Rider detach. Итог: **30 287 элементов (+2), 150 Each Player (−2), 324 правила (−2)**. Новых переменных и ожиданий нет. Компиляция без предупреждений; остальные 322 скомпилированных правила не изменились, действия отсоединения Rider совпадают с исходными. [Проверка внедрения](2026-11-15-ultimate-rider-merges-after.json), [скрипт проверки](2026-11-15-verify-ultimate-rider-merges.cjs). Игровая проверка ещё не выполнялась. Ниже сохранены исходные предложения и замеры до внедрения; скрипт экспериментов теперь пропускает уже внедрённые объединения.

Проверена текущая рабочая копия 15 ноября 2026 года, включая выбранный пользователем debug map pool. Исходники игрового режима не изменены. OverPy 9.7.21: **30 285 элементов, 326 правил**, из них **152 Ongoing — Each Player**, 45 Ongoing — Global, 90 Subroutine и 39 правил остальных событий игрока. Подпрограммы нельзя считать постоянно проверяемыми правилами Each Player.

Все числа ниже получены компиляцией отдельных вариантов относительно одной базы. Это результаты конкретных прототипов, а не доказательство минимально возможного размера. Ускорение сервера, причины поломки UI и полная эквивалентность в игре не измерялись.

## 1. Apothecary и сопротивление во время ультимейта

Источники: [PLAYER ULTIMATE DAMAGE RESIST](../src/abilities/hero_tuning.opy#L137), [APOTHECARY ULTIMATE RECHARGE](../src/abilities/augment_apothecary.opy#L66).

Оба правила имеют одинаковый вход: Team 1 и `isUsingUltimate() == true`. В начале правила сопротивления добавить:

```python
if eventPlayer.augmentId == Augment.APOTHECARY and eventPlayer.getHero() not in [Hero.DVA, Hero.DMON]:
    eventPlayer.augmentApothecaryReady = true
```

Затем оставить существующие применение сопротивления, ожидание окончания ультимейта и повторное применение модификатора. Отдельное правило Apothecary удалить. Его ранний `return` переносить нельзя: он прервал бы обработку сопротивления у остальных игроков. Исключение D.Va/D.Mon сохраняется; их заряд от урона остаётся в прежнем обработчике.

**Результат: 151 Each Player и 30 284 элемента.** Новые переменные, циклы и ожидания не нужны. Проверить начало/конец ультимейта, смерть во время него, Apothecary у обычных героев и меха-героев, пересечения с Dash и Super Nano.

Charge Battery пока не включать в тот же перенос автоматически: его условие дополнительно зависит от `isGameplayActive` и Enhancement. Простая проверка только в начале ультимейта не воспроизводит переход этих условий в true, когда ультимейт уже идёт.

## 2. Два отсоединения Rider

Источники: [отсоединение при смерти/невалидной цели](../src/game/zombie_types.opy#L485), [отсоединение от союзника](../src/game/zombie_types.opy#L516).

Одинаковые действия: очистить `botAbilityTarget`, сбросить `botIsAttached`, вызвать `detach()`. В обоих правилах нет ожиданий. Вынести общие условия Team 2, Widowmaker, отсутствие Wrestler-переносчика и активное прикрепление; остальные наборы условий объединить через `or`.

Сохранить все исходные проверки в соответствующих ветках: например, условие наличия `botTarget` из второго правила нельзя сделать общим для первого. Для этого случая обычное объединение `or` подходит: обе причины приводят к одному немедленному результату, а сброс `botIsAttached` выключает объединённое условие.

**Результат: −1 Each Player, +3 элемента.** Это осознанный обмен размера на число постоянных обработчиков. Предполагаемую пользу для сервера нужно измерить. Проверить прикрепление к игроку и зомби, смерть обеих сторон, CC, неуязвимость, телепортацию и перенос Wrestler.

## 3. Общий Melee для трёх Enhancement

Источники: [Zombie Hybrid](../src/abilities/enhancements.opy#L15), [Bulking Season](../src/abilities/enhancements.opy#L117), [Charge Battery placement](../src/abilities/enhancement_charge_battery.opy#L37).

У всех Team 1, живой игрок и удержание Melee. Enhancement взаимоисключающие: можно оставить общее правило, точные дополнительные условия каждой ветки и выбрать тело по `enhancementId`. Сохранить `wait(0.5, ABORT_WHEN_FALSE)` у Bulking/Battery, отпускание кнопки у Battery и независимые процедуры кулдауна. Нового общего таймера не требуется.

**Результат: −2 Each Player, +38 элементов.** Общий вход стал сложнее; ускорение из меньшего числа правил не следует. Эквивалентность этого прототипа предполагает стабильный `enhancementId` во время выполнения способности. В обычной игре выбор фиксирован, но меню позволяет его менять: перед внедрением проверить переход меню → игра и отсутствие незавершённой ветки при смене выбора. По приоритету элементов уступает первым двум кандидатам.

## Что не стоит склеивать обычным `or`

- **Кнопки голосования/выбора.** Сейчас отдельная кнопка получает собственный переход false → true. Если Ultimate остаётся зажатой и нажать Ability 1, общее условие `Ultimate or Ability1` остаётся true: новый голос может не обработаться. Нужен учёт фронтов каждой кнопки, дополнительные состояния либо отдельные контроллеры. Аналогичный риск у Melee/Interact в меню.
- **Очистку DoT и заражение.** Это параллельные процессы с периодами 0.25 и 1 секунда. Последовательное тело с общим `wait` меняет расписание и взаимодействие нанесения/снятия DoT.
- **Инвизы разных героев.** Три похожих тела не означают одинаковый жизненный цикл: разные способности завершают свои ожидания независимо. Смена героя/дублирование во время незавершённой ветки требует отдельного разбора; счётчик `invisibilityCount` должен корректно учитывать перекрытия.
- **CC status и BOT STUN MANAGEMENT.** У второго есть собственное окно обновления 0.125 секунды и восстановление флага после инициализации бота. Немедленная запись обоих флагов в одном месте меняет это поведение.
- **Телепорты, AI, Grapnel, Dash и HIGHRISE с разными ожиданиями.** Общий последовательный обработчик может задержать действие, которое сейчас выполняется параллельно.
- **Инициализацию, создание UI и выбор Enhancement/Augment.** У них различаются условия запуска и ожидания. Перенос в конец одного тела способен задержать интерфейс либо изменить момент и количество создаваемых сущностей.

## Событийные правила и UI

Объединение четырёх disconnect-cleanup не уменьшает Each Player и добавляет 28 элементов. Существующее глобальное очищение списков при выходе содержит ожидания: не включать его в общий последовательный cleanup без сохранения независимого выполнения.

Объединение четырёх обработчиков статусов от попаданий добавляет 50 элементов и убирает встроенную фильтрацию событий по герою. Не следует переносить их под общие условия `PLAYER DEALT DAMAGE`: там есть `victim != attacker` и `eventDamage > 0`, которые не совпадают с исходными условиями всех четырёх правил. Нулевой урон нельзя исключать без отдельного обоснования.

Само количество правил с `eventPlayer` пока не установлено как причина поломки UI. В [debug HUD](../src/debug/debug.opy#L36) уже выводятся Text IDs, Entity IDs и текущая/средняя/пиковая Server Load. Зафиксировать эти значения до и после объединений при одинаковом числе людей, ботов, выбранных способностях и объективе. Отдельно записывать момент поломки UI: вход/переподключение, смена героя, начало игры, смена цели. Сокращение правил само по себе не сокращает число создаваемых HUD/эффектов и их переоценок.
