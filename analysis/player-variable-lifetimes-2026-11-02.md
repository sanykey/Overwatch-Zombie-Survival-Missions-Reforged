# Временные значения и неиспользуемые записи playervar — 2026-11-02

Исходная версия: `fddc95a`, **108 физических playervar, 99 globalvar, 27 218 элементов**.
Пакет внедрён: **107 физических playervar, 99 globalvar, 27 188 элементов** (−1 слот, −30 элементов).
В `variables.opy` осталось **76 алиасов**; одиночные роли стали физическими переменными
`botTarget`, `botTeleportPosition` и `botReigniteRisePosition` с комментариями и группой Team 2.

**Уточнение первоначальной оценки:** у `botPotentialTargetList` пропущено чтение в переоцениваемом
тексте расстояния до босса. Расчёт перенесён в `tmp1`, но итоговый список обязательно сохраняется
обратно в поле для этого текста. Поэтому безопасный итог — **27 188**, а не первоначальные 27 186.
Необязательные удаления записей Bomber/Sigma/возврата босса не внедрялись.

Освобождён **один физический слот**: `botMutationOutlineColor` заменён
на временный цвет с обязательным `evalOnce` в аргументе контура. Несколько других ролей тоже локальны,
но их физические слоты остаются нужны другим потребителям.
Физических переменных, у которых совсем нет явных либо неявных чтений, не найдено.
Отсутствие чтений отдельного алиаса не доказывает, что его записи не используются через другие алиасы.

## Почему цвет мутации можно сделать временным

В [mutationsMacro](../src/subroutines.opy#L78) все пять присваиваний цвета выполняются
непосредственно перед `startForcingOutlineFor`, без ожиданий между ними и этим действием.
При отсутствии мутации код останавливает контур через `stopForcingOutlineFor`.
Других записей или обычных чтений `botMutationOutlineColor` нет.

Простая замена поля на `tmp2` без захвата значения недостаточна: длительный контур
не должен зависеть от последующих изменений общего scratch.
Внедрённый вызов:

```python
eventPlayer.startForcingOutlineFor(getAllPlayers(), true, evalOnce(tmp2))
```

Контур получает сохранённый результат вычисления цвета. После действия `tmp2` можно использовать
в других правилах и для других игроков. Сброс `tmp2 = null` в ветке без мутации не требуется:
там цвет не читается, а существующий контур останавливается.

В проверенном варианте последняя ветка выбора мутации `elif ... == 5` превращена в `else`,
чтобы запись `tmp2` была гарантирована на каждом пути перед чтением.
Это опирается на проверенный диапазон: [enableMutationsMacro](../src/global_startup.opy#L74)
формирует список только из включённых ID 1–5 и удаляет нули; успешный выбор берётся из непустого списка.
Другие присваивания ID ограничены сбросом в 0 в ветке без мутации.
Проба проверяет источники ID и соответствие цветов всем пяти ID.
Остальные действия Heavy в последней ветке сохраняются.

Нельзя просто проигнорировать предупреждение о чтении `tmp2` до записи:
обычный анализ CFG не знает о диапазоне случайно выбранного ID и видит путь мимо всех пяти `if/elif`.

Дополнительно проверена альтернатива без временной переменной:

```python
evalOnce([null, Color.PURPLE, Color.VIOLET, Color.ROSE, Color.LIME_GREEN, Color.BLACK][eventPlayer.botMutationId])
```

Она также освобождает поле цвета, но даёт **27 223 элемента (+5)**.
Вариант с `tmp2`, захватом цвета и исчерпывающей последней веткой даёт **27 212 (−6)**.
Фиксированный оранжевый контур минибосса не использует это поле и сохраняется.

## Записи без чтений: физические поля и алиасы

В исходной ревизии **107 из 108 физических полей имеют явные обращения на чтение**.
В текущей сборке поле цвета удалено; осталось 107 физических полей.
Оставшееся поле, [powerUpAirStrikeIndex](../src/supply_drops.opy#L204), — счётчик `For Player Variable`.
Его неявно читает сам цикл, который управляет 50 взрывами и содержит `wait(0.125)`.
Это не неиспользуемая переменная и не кандидат для общего tmp.

Среди алиасов без явных чтений обнаружены следующие случаи:

| Имя | Записи | Оценка |
|---|---|---|
| `botIsBomberPrimed` | `true` перед `explosionWarning`, `false` внутри неё | У флага Bomber нет собственного потребителя; кандидат на удаление двух записей. Физический слот общий, его время жизни при смене героя надо учитывать. |
| `botReturnPosition` | снимок позиции глаз и последующий 0 | У имени нет чтений, но общий слот читается как `botReturnTime`. Удаление обеих записей не доказано безопасным. |
| `botAbilityState` | общий сброс в `botRespawnInitialization` | Инициализация `actorAbilitySlot1` для других ролей. Сохранять. |
| `botAuxiliaryState` | сброс при инициализации и после захвата Sigma | Инициализацию сохранять. Сброс только в обработчике Sigma — отдельный кандидат: у Sigma нет потребителя вторичного состояния, но старые обработчики при смене героя требуют проверки. |
| `botChargerWindupProgress` | заголовок `for` | Есть неявные чтения счётчика циклом; внутри есть ожидания. Сохранять. |
| `botEnsnarerUltimateIndex` | заголовок `for` | Есть неявные чтения счётчика циклом; внутри есть ожидания. Сохранять. |

Для **`botIsBomberPrimed`** прямые записи находятся в
[Bomber](../src/zombie_types.opy#L75) и [explosionWarning](../src/zombie_types.opy#L1473).
Удаление обеих в пробе уменьшает размер на **2 элемента**, но не освобождает playervar:
`actorAbilitySlot1` по-прежнему нужен другим героям и Rescue.
Успешная компиляция сама по себе не доказывает отсутствие наблюдения через другие роли общего слота.

Удаление только [сброса botAuxiliaryState в Sigma](../src/zombie_types.opy#L955)
уменьшает размер на **1 элемент**, без освобождения слота.
Общий [сброс при респауне](../src/subroutines.opy#L719) нужен для инициализации других ролей.

Особенно важно не объявлять автоматически неиспользуемыми записи **`botReturnPosition`**.
`bossReturn()` вызывается и из [обработчика смерти босса](../src/objective_types/objective_type_bosses.opy#L134),
и из [правила таймера возврата](../src/objective_types/objective_type_bosses.opy#L186).
Внутри подпрограммы есть ожидания, а другое правило может читать тот же физический слот
через `botReturnTime` в `waitUntil` и последующем условии.
Удаление обеих записей даёт −3 элемента в пробе, но **этот вариант отклонён по недоказанной
безопасности асинхронного общего состояния**. В частности, нельзя считать последующий сброс в 0
ненужным только потому, что один из двух вызывающих обработчиков тоже сбрасывает таймер.

## Ложные кандидаты на локальную переменную

- **`botCandidateTarget`**: при пустом `botPotentialTargetList` цикл в `selectTarget` не выполняет
  присваивание, но далее старый кандидат читается и копируется в `botTarget`.
  Общий tmp вместо поля взял бы случайное значение другого правила/актора.
  Для освобождения поля сначала нужно отдельно определить поведение при пустом списке.
- **`botSpawnWaypoint`**: `updateBotSpawnPoints()` вызывается не только сразу после записи waypoint,
  но и при смерти/выходе из телепорта. Там используется ранее сохранённый снимок.
- **`powerUpTurretDirection`**: кроме расчёта очередного выстрела, его читает
  [переоцениваемый луч турели](../src/supply_drops.opy#L265). Между выстрелами есть ожидания.
  Захват единственного направления при создании луча изменил бы поведение турели.
- **`visualCleanupIndex`**: циклы уничтожения визуальных объектов содержат `wait()`
  и в [botEntityManagementMacro](../src/subroutines.opy#L128), и в управлении иконками цели игрока.
  Проба замены ботского цикла на `tmp0` отклонена CFG-проверкой:
  `botRespawnInitialization: tmp0 live across Wait(False, Ignore Condition)`.
- **`rescuePotentialLeaderList`**: это не только локальный расчёт лидера в одном правиле.
  Список читается из [условия другого правила и обработки GROUP UP](../src/objective_types/objective_type_survivor_rescue.opy#L149)
  и сохраняется между проходами с `wait(0.25)`. Поэтому `candidateTargetList` нельзя удалить,
  даже если роли выбора цели зомби и столкновений Barricade перенесены в scratch.
- Счётчики длительности, chased-позиции, цели оживления/извлечения, индексы обмена предметами,
  ID долгоживущих эффектов и данные переподключения сохраняются между ожиданиями или обработчиками.

## Проверенный консервативный пакет — внедрено

Совместная проба включает `rescuePathIndex → tmp0`, `botReigniteSource → tmp0`,
`enhancementBarrierTarget → tmp2`, расчёт `botPotentialTargetList → tmp1` с сохранением снимка для текста босса
и `botMutationOutlineColor → tmp2` с захватом цвета и исчерпывающим выбором ветки.

Результат: **107 playervar, 99 globalvar, 27 188 элементов (−30)**.
Проверка scratch проходит для 42 правил с временными глобальными переменными;
они не используются в условиях правил, не остаются живыми через ожидания/вызовы,
а цвет контура явно захвачен через `Evaluate Once` в скомпилированном Workshop.
Непроверенные удаления записей Bomber/Sigma/возврата босса в этот пакет не входят.

Переименования и очистка алиасов не меняют действия: `combatTargetSlot` стал `botTarget`,
при этом прежний `currentCombatTarget` в очистке целей тоже заменён на `botTarget`;
`aiLocationSlot` стал `botTeleportPosition`; `botReigniteMotionSlot` стал `botReigniteRisePosition`.
Эти три поля теперь находятся в группе Team 2. `candidateTargetList` сохраняет три алиаса:
`botPotentialTargetList`, `rescuePotentialLeaderList`, `enhancementBarrierTargetList`.

Все 231 скомпилированное правило совпадают с согласованным преобразованием базы `fddc95a`
после нормализации трёх физических имён. Сборка через обычные `#!include` также проверена,
локальный `src/main.ws.txt` обновлён. Проверка глобальных фаз сохранена отдельным сравнением
с промежуточной ревизией, затем проверен переход к текущему пакету.

Выполнено 15 компиляционных проб без предупреждений компилятора, включая отклонённые варианты.
Вариант без сохранения итогового списка целей отдельно помечен отклонённым: проверка времени
жизни scratch сама по себе не замечает потерю данных, нужных постоянному тексту.
