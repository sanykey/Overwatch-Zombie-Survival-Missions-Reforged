## P.U.P.: общая пара цвета и видимости луча — −6

В пяти местах повторяется строго одна и та же последовательность:

```python

```

Предлагается общий `resetPupColorAndBeam()` с ровно этими двумя действиями. Места: конец P.U.P. TARGET, начало P.U.P. CONTROL, окончание заморозки, окончание лазерной атаки и начальная настройка enhancement.

Нельзя переносить их в общий helper: например, при старте CONTROL цель должна сохраниться, а после лазера исходник не сбрасывал freeze aura. Новый helper не использует scratch, не содержит wait, условий, loops или асинхронных starts; Event Player сохраняется. Все переменные остаются в прежних владельцах. В игре проверить первичную настройку P.U.P., поиск/потерю цели, дальнюю заморозку, ближний лазер, прерывания и возврат к default chase; проверить цвет, луч и freeze aura отдельно.

## Камера: сравнение вместо modulo — −1

```python
# Было
eventPlayer.cameraMode = (eventPlayer.cameraMode + 1) % 2
# Предлагается
eventPlayer.cameraMode = eventPlayer.cameraMode != CameraMode.PRECISE
```

В `variables.opy` контракт human camera preference допускает **0/1/2**. Поэтому самый короткий вариант `not eventPlayer.cameraMode` **не включён**: при входном 2 исходник даёт 1, а not даёт False/0. Это обнаружено при сверке контракта; сужать его и исправлять комментарий на 0/1 ради этого варианта не предлагается.

В рекомендуемом сравнении переходы сохранены:

| Старое значение | Исходный modulo | Сравнение != PRECISE (1) |
|---|---:|---:|
| 0 / Null / False | 1 | True / 1 |
| 1 / True | 0 | False / 0 |
| 2 | 1 | True / 1 |

Полученный boolean совместим с текущими читателями 0/1: проверкой `== CameraMode.PRECISE` и индексом массива подписи Normal/Precise. Кнопки, Conditions, применение камеры и сообщение после переключения не меняются. Поле по контракту принадлежит человеку Team 1; роль массива botResourceIconIdList на Team 2 не затрагивается. Нельзя обобщать преобразование на произвольные числа: например, для других нечётных чисел сравнение и modulo могут расходиться.

Проверены **600 переходов**: по 100 последовательных нажатий для шести исходных состояний 0/1/2/Null/False/True, включая числовой режим, выбор Precise и текст подписи. Во всех исходниках обнаружен ровно один writer cameraMode. Модель использует числовую интерпретацию boolean, принятую текущим Workshop-кодом; нативный рендер и пользовательский ввод не эмулировались.

В игре нужны переключения Normal/Precise, переключение после респавна/смены героя и после временного отключения камеры при прицеливании, сохранение предпочтения, а при проверке старого значения 2 — первый переход в Precise.

## Проверка выделения подпрограмм

Скомпилированные тела двух новых подпрограмм подставлены вместо Call Subroutine. При этом аудитор пересчитывает относительные Skip/Skip If и все смещения в скомпилированных switch-таблицах: один Call заменяется двумя либо тремя прежними командами. Это важно для P.U.P. внутри enhancement switch и для условных путей атак.

После такого разворачивания последовательности команд и цели переходов затронутых правил побуквенно совпадают с исходными (с канонической записью числовых Skip-offsets). Неизвестные динамические Skip-формы аудитор не пропускает молча. Отдельно проверены отсутствие waits/управления потоком в новых телах, тип события Subroutine и допустимая длина имён.

Это структурная проверка экспорта, не запуск игрового планировщика. Для двух локальных замен камеры/revive поведение проверялось по условиям выше, а не через подстановку helper.
