### Прямой выбор носителя — главный кандидат

В `ZOMBIE GETS RESOURCE VALUE/OBJECTIVE GIVES POWERUPS` сейчас выполняется:
выбор первого подходящего игрока Team 2 → поиск его индекса в Team 2 → новая
копия списка Team 2 → чтение игрока по найденному индексу.

Достаточно сразу сохранить выбранного игрока в существующий tmp1:

```python
#!define biowasteCarrier tmp1
biowasteCarrier = getPlayers(Team.2).filter(lambda player: player.biomorphingResourceAmount != BIOMORPHING_RESOURCE_AMOUNT)[0]
```

Убираются `biowasteCarrierIndex`, `biowasteCarrierCandidateList` и соответствующие
промежуточные присваивания; физические globalvar tmp0/tmp1 остаются общими.
Тип ресурса, порядок присвоения amount/type, `biowasteOutputMacro()` и его
перетасовка очереди остаются на прежних местах. Носитель в tmp1 переживает
синхронное переиспользование tmp0 под выданный тип. Helper перетасовки не трогает tmp1.

Список Team 2 состоит из сущностей игроков. При наличии кандидата обратное
индексирование исходного списка возвращает ровно того же игрока. В отсутствие
кандидата `First Of` возвращает 0, поиск его индекса даёт −1, последующее чтение
несуществующего элемента также даёт 0. Поведение чтения вне массива описано
в [Workshop Value In Array](https://workshop.codes/wiki/articles/value-in-array)
и в метаданных установленного OverPy. Проверены 511 моделей наборов игроков
размером 0..8 со всеми сочетаниями допуска, включая пустую команду и отсутствие
подходящего носителя. Это модель документированной семантики, не игровой прогон.

**Не добавлять ранний return при отсутствии кандидата:** исходный код продолжал
обработку очереди даже в этом случае. В предложении это поведение сохранено.
Между исходными операциями нет wait или вызовов с побочными эффектами.

Вместе с размером сокращается работа: исключаются обратный линейный поиск
индекса, повторные получения команды и лишние записи/чтения scratch.
Фактическое изменение Server Load не измерялось.

### Подстановка позиции при подборе — ещё −2

В `BIOWASTE IS PICKED UP` позиция ближайшего ресурса сохраняется в tmp0 только
для следующего вычисления индекса. Других читателей `biowastePickupPosition` нет.
Можно оставить один существующий alias для индекса:

```python
#!define biowastePickupIndex tmp1
biowastePickupIndex = biomorphingResourcePositionList.index(sorted(biomorphingResourcePositionList, lambda x: distance(eventPlayer, x))[0])
```

Сортировка, расстояния и поиск первого вхождения остаются прежними. Повторяющиеся
координаты обрабатываются так же; все четыре удаления и уничтожение двух visual IDs
получают тот же индекс. Ничего не переносится через ожидание, сортировка не повторяется.
Экономия относится к промежуточной записи/чтению, а не к алгоритму сортировки.
