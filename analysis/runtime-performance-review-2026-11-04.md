## 1. Поиск целей и видимость ботов — высокий приоритет

Места: [bots_game_in_progress.opy:235](../src/bots_game_in_progress.opy#L235), [bots_game_in_progress.opy:266](../src/bots_game_in_progress.opy#L266), [subroutines.opy:670](../src/subroutines.opy#L670).

`BOT TARGET VISIBLE` содержит обход `playerTargetList` с расстояниями и `isInLoS` прямо в условиях правила. После этого `selectTarget()` заново строит списки, делает две сортировки и проверяет видимость кандидатов. Отдельное правило `DESELECT BOT TARGET` снова проверяет видимость текущей цели. Настройка популяции допускает до 23 зомби.

`wait(1)` внутри `BOT TARGET VISIBLE` ограничивает повторное выполнение тела, но не выносит дорогое выражение из секции `conditions`. Нельзя считать этот код проверкой видимости строго раз в секунду только на основании этого ожидания.

Кандидат: перенести поиск новых целей в управляемый цикл с дешевыми условиями запуска; сначала формировать допустимых кандидатов, затем выполнять проверки видимости. Прототипировать интервал 0,1–0,25 секунды, распределяя обновления ботов по времени. Проверку потери текущей цели рассматривать отдельно: увеличение ее интервала меняет скорость реакции на стены и невидимость.

Сохранить приоритеты минибоссов, dummy-целей, Pharah и игроков ниже бота, а также `botPotentialTargetList`, который читает HUD босса. Сокращение повторных проверок перспективнее самостоятельной замены двух сортировок небольшого массива игроков.

## 2. Турель — высокий приоритет

Место: [supply_drops.opy:264](../src/supply_drops.opy#L264).

Во время 30-секундной работы цикл имеет шаг 0,125 секунды — **240 итераций**, номинально 8 в секунду без учета времени выполнения. В каждой итерации выполняется `.any(isInLoS...)`; если условие истинно, следующий `.filter(isInLoS...)` снова обходит живых зомби, после чего результат сортируется. В переоцениваемом выражении ствола на строке 276 есть еще один независимый обход с видимостью.

Кандидат: один раз за итерацию получить список видимых зомби и использовать его для проверки наличия цели и выбора направления. Для эффекта хранить отдельный флаг наличия подходящей цели. Можно дополнительно отделить период выбора цели от периода выстрелов, сохранив выстрелы каждые 0,125 секунды.

Оговорка: текущая `.any()` исключает телепортирующихся ботов, а `.filter()` для выбора направления — нет. Объединение этих двух предикатов меняет поведение. Для сохранения поведения список должен содержать всех видимых, а флаг — учитывать `not botIsTeleporting` отдельно. Замена двух raycast выстрела одним требует отдельного разбора попаданий и препятствий; автоматически ее не предлагать.

## 3. Возврат босса: видимость по всей сетке — простой первый кандидат

Место: [objective_type_bosses.opy:211](../src/objective_types/objective_type_bosses.opy#L211).

`bossReturn()` фильтрует весь `mapGridList` предикатом, содержащим `isInLoS` и ограничение расстояния 5–20 м. Генератор стремится собрать до **900 точек**. В скомпилированном коде это один `Filtered Array` с вложенными `And`.

Кандидат: отдельным присваиванием сначала отобрать точки с `5 < distance < 20`, затем проверять видимость только у отобранных. Это явно ограничивает вход дорогого прохода пространственными кандидатами; перестановка частей одного `and` такой структуры не обеспечивает. Если таких точек `k`, второй фильтр получает `k` точек вместо `N` точек всей сетки. Значения `k` и фактическое число вычислений движка здесь не измерялись.

Проверен прототип **только в памяти**: компилятор сохранил два отдельных прохода; сборка **25 305 → 25 307 (+2 элемента)**. Дополнительные переменные не нужны: используется тот же синхронный `tmp0`, между проходами нет ожидания. В обычном состоянии мира сохраняются порядок и набор кандидатов и случайный выбор точки; игровую проверку это не заменяет.

Эта операция сравнительно редкая, поэтому ее вклад в среднюю нагрузку может быть ниже поиска целей. Проверять прежде всего пики во время возврата нескольких боссов.

## 4. Лазерная баррикада — высокий приоритет при скоплении зомби

Место: [enhancements.opy:223](../src/enhancements.opy#L223).

В условиях четыре независимых `.any()` по живым зомби; одно выражение содержит расчет расстояния до отрезка. В теле затем снова считается полный геометрический фильтр. Цикл завершается `wait()` без явного интервала. Для каждого попавшего зомби дополнительно выполняются raycast нормали поверхности и сортировка двух опорных точек. При нескольких баррикадах объем работы растет.

Кандидат: вынести обнаружение столкновений в контролируемый проход, переиспользовать геометрию в пределах этого прохода и заменить сортировку двух точек прямым сравнением. Более редкую проверку столкновений рассматривать только вместе с сохранением баланса.

Нельзя просто объединить четыре `.any()` в одну: сейчас каждое условие может выполняться на разных зомби. Это влияет на вход в тело и остановку/запуск регенерации здоровья. Нельзя просто увеличить `wait()`: частота импульсов и удержание зомби изменятся, даже если урон баррикаде ограничен статусом `ROOTED`. Уже выполненная замена тригонометрии на `dotProduct` видна в текущем коде; повторно ее предлагать не нужно.

## 5. Повторные сортировки и raycast в визуальных выражениях

Места: [global_game_in_progress.opy:14](../src/global_game_in_progress.opy#L14), [subroutines.opy:332](../src/subroutines.opy#L332), [supply_drops.opy:74](../src/supply_drops.opy#L74), [enhancements.opy:54](../src/enhancements.opy#L54).

Выбор аптечки по углу взгляда повторен трижды между текстом, его позицией и иконкой. Выбор ресурса Biomorphing повторен в тексте и позиции. Подсказка подбора усиления отдельно проверяет существование подходящего предмета и повторяет геометрию при фильтрации/сортировке. Предпросмотр баррикады содержит два одинаковых raycast для концов луча и отдельный raycast проверки дальности.

Компиляция подтвердила, что две сортировки аптечек внутри одного `Create In-World Text` остаются отдельными выражениями: их нельзя считать автоматически вычисленными один раз. Переоценка задается параметрами визуальных объектов; выполнение создающего правила один раз не означает однократное вычисление этих выражений.

Кандидат: хранить выбранную позицию/цель отдельно для каждого игрока и обновлять ее по необходимости с ограниченной частотой. Для общей точки предпросмотра луча использовать отдельный кэш позиции попадания. Проверить плавность отображения, переключение цели при повороте камеры и обнуление кэшей при исчезновении предметов, смерти и смене фазы.

Не заменять выбор по углу взгляда ближайшим по расстоянию: это другая логика. Не записывать индивидуальный результат в одну общую глобальную переменную и не использовать общие временные `tmp*` в переоцениваемом HUD. Вводимый серверный цикл обновления сам создает нагрузку; сначала сравнить его с исходным вариантом, особенно при коротких списках.

## 6. Поиск точек телепортации — средний приоритет

Место: [bots_game_in_progress.opy:445](../src/bots_game_in_progress.opy#L445).

Внутри поиска точки повторяются фильтры списка спавнов и `botSpawnPointList.index(x)` для каждого кандидата. Затем повторяется `index` выбранной позиции. Для большого списка это повторные поиски по тому же массиву. Одновременно точку могут искать многие боты.

Кандидат: формировать список допустимых индексов, проверять позицию и таймер через один индекс и сохранять выбранный индекс до ближайшего ожидания. Не сохранять индексы через `wait`: другой бот может удалить точку. Ограничить число попыток за один проход и при отсутствии `playerTargetList` приостанавливать поиск до появления цели с корректным восстановлением состояния.

Последняя защита одновременно устраняет лишнюю работу при пустом списке целей. Это известный пограничный случай, уже отмеченный в комментариях исходника. Наивный `return` опасен: бот может остаться невидимым, без гравитации и в состоянии телепортации.

### 8. Силовое поле: повторное получение живых зомби

Место: [supply_drops.opy:156](../src/supply_drops.opy#L156).

Силовое поле выполняет цикл в течение 10 секунд с шагом 0,032 секунды — примерно 313 итераций. Внутри обхода по зомби выражение `getLivingPlayers(Team.2)[index]` встречается трижды: для расстояния, получателя импульса и направления. Это до нескольких тысяч исполнений тела внутреннего цикла при большой популяции, хотя поле действует лишь на ближайших зомби.

Кандидат: получить список живых зомби один раз в начале каждой внешней итерации, использовать этот снимок для длины и индексации. При необходимости отдельно проверить предварительный отбор ближайших существующим предикатом расстояния. Частоту импульсов сохранять.

Прототип снимка проверен компиляцией: **25 305 → 25 305**, без новых переменных. В скомпилированном правиле три вхождения `All Living Players(Team 2)` заменяются одним присваиванием снимка перед внутренним циклом. Это число узлов выражений, а не измеренное число вычислений движка. `tmp1` потребляется до ближайшего `wait`, внутри обхода нет подпрограмм и ожиданий. Прототип находится в скрипте статической проверки.

### 9. Pyrotechnic: очередь повторных попаданий

Место: [enhancements.opy:287](../src/enhancements.opy#L287).

Каждое подходящее попадание добавляет жертву в `enhancementPyroHitList`, включая дубликаты. Обработчик берет первую цель, фильтрует оставшуюся очередь ради числа ее повторений и удаляет ее из очереди. Это повторные проходы по списку попаданий для каждой уникальной жертвы; при многих разных жертвах объем работы может расти квадратично относительно размера очереди. Количество уникальных жертв на практике ограничивает популяция.

Кандидат: агрегировать число попаданий по жертве, хранить уникальных жертв и счетчики, а не повторные ссылки. Для текущей формулы `min(4 * count, 30)` достаточно различать значения 0–7 и «8 или больше». Уменьшение очереди перспективно для скорострельных и массовых атак, но добавление поиска счетчика на каждом попадании тоже стоит времени: сравнивать оба варианта под нагрузкой.

Сохранить пакетную обработку, паузу 0,5 секунды, половинный урон боссам и отдельный контекст атакующего. Переход на один общий счетчик жертвы или отдельный DoT на каждую пулю меняет механику. Связи хранить по сущности игрока; индекс слота нельзя считать постоянной идентичностью после пересоздания бота.

### 10. No Cooldowns: частые записи неизменных значений

Место: [supply_drops.opy:177](../src/supply_drops.opy#L177).

Каждые 0,032 секунды правило сбрасывает восемь кулдаунов и выставляет три значения зарядов (для Reaper — два). При полном 15-секундном действии это примерно 469 итераций и около **5 159 выполнений действий записи** для обычной ветки. Это арифметическая оценка по исходнику, без учета прерывания/перезапуска и фактического времени выполнения.

Кандидат: прототипировать обновления только для применимых герою кнопок и фактически потраченных зарядов/кулдаунов. Для кнопок, которые нельзя надежно сопоставить герою, оставить исходную обработку. Условные чтения сами стоят времени: добавлять `if cooldown > 0` перед каждой записью без замера может оказаться невыгодно. Не увеличивать интервал автоматически — это меняет отзывчивость усиления. Смена героя во время эффекта требует обновления списка кнопок.

### 11. Путь сопровождаемого выжившего

Места: [objective_type_survivor_rescue.opy:62](../src/objective_types/objective_type_survivor_rescue.opy#L62), [objective_type_survivor_rescue.opy:114](../src/objective_types/objective_type_survivor_rescue.opy#L114), [objective_type_survivor_rescue.opy:127](../src/objective_types/objective_type_survivor_rescue.opy#L127).

Путь пополняется при перемещении лидера, а верхний предел длины не задан. Если лидер продолжает двигаться, пока NPC отстал или застрял, список способен расти. Выражение движения содержит `.any(...)` и повторный `.filter(...).last()` по тому же пути; удаление пройденного участка дополнительно сортирует весь путь ради одной ближайшей точки, затем ищет ее индекс.

Кандидат: искать индекс ближайшей точки одним линейным проходом с сохранением первого минимума при равенстве, переиспользовать вычисления руления и убирать заведомо пройденные точки. Варианты ограничения или упрощения пути требуют проверки навигации: нельзя просто отбрасывать старые точки и срезать углы маршрута.

Наивная замена удаления на `slice` требует отдельного доказательства: исходное `remove(filter(...))` удаляет по значениям, поэтому при повторяющихся точках может удалить и совпадения за выбранным индексом. В предыдущем аудите `slice` также не дал экономии элементов; это не исключает другие изменения алгоритма.

### 12. Декоративные эффекты Bounce Pad и Air Strike

Места: [supply_drops.opy:385](../src/supply_drops.opy#L385), [supply_drops.opy:211](../src/supply_drops.opy#L211).

Bounce Pad проверяет игроков 480 раз за 60 секунд и отдельно посылает всем игрокам декоративное кольцо каждые 0,25 секунды — около 240 запусков эффекта за активацию. Air Strike делает 50 взрывов, каждый с четырьмя вызовами `playEffect` для всех игроков — 200 вызовов визуальных/звуковых эффектов.

Кандидат для клиентской нагрузки и трафика: сократить частоту декоративных колец или показывать дальние косметические эффекты ограниченному кругу зрителей. Проверки прыжка, радиусы и урон сохранять с исходной частотой. Это осознанное изменение визуальной детализации; сокращение числа вызовов не доказывает снижение Server Load, а фильтрация зрителей добавляет собственные вычисления. Проверять FPS и восприятие предупреждений об опасности.

### 13. Меньшие кандидаты

- [enhancements.opy:518](../src/enhancements.opy#L518): Hitchhiker сортирует массив из двух игроков и затем строит второй массив через `concat().exclude()`. Выбор получателя/донора можно выразить прямым сравнением нормализованного здоровья. Сам по себе эффект небольшой; формулу переноса здоровья сохранять.
- [global_startup.opy:128](../src/global_startup.opy#L128): каждую секунду таймеры респавна сортируются после одинакового вычитания единицы. При поддержании сортировки во всех местах изменения очереди повторную сортировку можно исключить. Сначала проверить все добавления, принудительные изменения и отрицательные значения; массив небольшой, приоритет низкий.
- [debug.opy:10](../src/debug.opy#L10): цикл отладочных усилений сейчас имеет только ожидание и повтор — все изменения характеристик закомментированы. Его можно отключить до возвращения усилений. Диагностический HUD нагрузки при этом полезен для измерений и должен рассматриваться отдельно.

Из новых кандидатов начать со снимка списка для силового поля. Pyrotechnic и путь NPC имеют больший потенциальный алгоритмический эффект, но требуют сценарных проверок. No Cooldowns и косметические эффекты лучше менять после замеров, поскольку они затрагивают отзывчивость и внешний вид.

## Третий проход: расходы долгого матча и повторные активации

### 14. Список минибоссов сохраняет пустые записи

Места: [subroutines.opy:28](../src/subroutines.opy#L28), [bots_game_in_progress.opy:150](../src/bots_game_in_progress.opy#L150), [subroutines.opy:751](../src/subroutines.opy#L751).

Создание минибосса делает `miniBossList.append(eventPlayer)`, а обычная ветка смерти заменяет запись нулем. Нули в этой ветке не удаляются и при следующем создании не переиспользуются. Поэтому последовательность «создать минибосса — убить его — создать следующего» увеличивает длину массива при неизменном количестве живых минибоссов. Есть отдельное удаление при превращении в босса задания; оно не очищает нулевые записи от обычных смертей.

Список читается в условиях многих бот-правил, обработчиках урона, выборе целей и проверке `.any(entityExists)`. Рост числа пустых записей увеличивает размер входа этих операций. Этот кандидат особенно полезен для длинных матчей и не требует сокращения игрового контента.

Кандидат: удалять умершую сущность либо переиспользовать/компактировать пустые записи перед добавлением. Сначала проверить все читатели: в [objective_type_bosses.opy:16](../src/objective_types/objective_type_bosses.opy#L16) есть подозрительное обращение `miniBossList[player]` по индексу вместо обычной проверки принадлежности. Менять представление списка без разбора этого места нельзя считать доказанно безопасным. Во всех остальных найденных читателях используются принадлежность или `.any()`, а не значимая позиция конкретного минибосса.

### 15. Лимит предметов на земле не является общим

Места: [supply_drops.opy:24](../src/supply_drops.opy#L24), [supply_drops.opy:96](../src/supply_drops.opy#L96), [power_ups.opy:90](../src/power_ups.opy#L90), [objective_type_biomorphing.opy:100](../src/objective_types/objective_type_biomorphing.opy#L100).

Комментарий «Limited to 12 power ups» относится к условию запуска снабжения. Оно не ограничивает все добавления: ручной сброс, сброс при смерти и выдача четырех наград Biomorphing добавляют предметы отдельно. Даже само открытие ящика добавляет весь пакет без ограничения до оставшихся мест. Между проверкой начала генерации и открытием ящика проходят ожидания.

Следовательно, 12 нельзя использовать как гарантированную верхнюю границу размера `supplyPowerUpPositionList`. Каждый предмет получает эффект и подпись, а логика подсказок/подбора обходит и сортирует список. Удаление найдено при подборе; автоматического срока жизни или общего удаления избытка в этих путях нет. Увеличение числа предметов расходует также общий бюджет текстов и эффектов.

Кандидат: единая функция регистрации наземного предмета, через которую проходят все источники. В ней можно контролировать общий бюджет и, если это соответствует желаемой механике, срок жизни или удаление старых предметов. Нельзя просто пропустить добавление позиции: параллельные массивы ID типов, позиций и визуальных объектов должны оставаться согласованными, а сбрасываемый предмет не должен молча теряться. Это изменение политики ресурсов, которое нужно согласовать с игровым дизайном при реализации.

### 16. Фильтры видимости, не зависящие от зрителя

Места: [players_game_in_progress.opy:122](../src/players_game_in_progress.opy#L122), [players_game_in_progress.opy:126](../src/players_game_in_progress.opy#L126), [subroutines.opy:149](../src/subroutines.opy#L149), [subroutines.opy:170](../src/subroutines.opy#L170).

В исходниках найдено 50 выражений вида `getAllPlayers().filter(lambda _: ...)`, где параметр зрителя не используется. Пример: `getAllPlayers().filter(lambda _: eventPlayer.isReviving)`. При неизменном состоянии результат — либо весь список, либо пустой список; фильтрация по отдельным игрокам не нужна.

Для выражений с булевым условием можно проверить замену на `getAllPlayers() if condition else []`, сохраняя исходную переоценку видимости. Для условий с `evalOnce`, числовыми значениями и `localPlayer` нужен отдельный разбор, а не массовая текстовая замена.

Проверен набор из семи простых замен для заражения/реанимации, газового снаряда и щупальца: **25 305 → 25 312 (+7)**, без предупреждений с текущими подавлениями. Компиляция сохраняет условный выбор списка вместо фильтра. Это кандидат для снижения повторной работы при переоценке, но не для экономии элементов; насколько он быстрее в движке, не измерено. Прототип включен в скрипт статической проверки и не внедрен.

### 17. Повторный запуск расходников с незавершенными ожиданиями

Место: [supply_drops.opy:472](../src/supply_drops.opy#L472).

В скомпилированном `powerUpUsage` все 11 асинхронных вызовов расходников используют `Start Rule(..., Restart Rule)`. Долгие подпрограммы имеют ожидания и очистку в конце. Повторное применение того же расходника в контексте одного игрока поэтому требует явного контракта: продление таймера, перенос позиции, добавление в очередь либо запрет повторной активации. Текущий перезапуск не следует считать полноценной реализацией любого из этих вариантов.

Это прежде всего вопрос стабильности и корректного завершения эффектов, а уже затем производительности. В репозитории есть [отдельный аудит](start-rule-crash-report-2026-11-04.md). Текущий `main.opy` подавляет `w_start_rule_crash`, поэтому ноль предупреждений при обычной компиляции не подтверждает безопасность повторов.

Не заменять все вызовы на `NOOP`: `powerUpUsage` после запуска обнуляет предмет, а пропущенная активация тогда может списать его без эффекта. Следует отделить единственный исполнитель длительного эффекта от запросов на его продление/обновление и проверить очистку при выходе владельца, смене фазы и повторной активации. В этом проходе накопление объектов и падение сервера не воспроизводились.

### 18. Поиск точки снабжения не имеет общего предела попыток

Место: [supply_drops.opy:34](../src/supply_drops.opy#L34).

Цикл продолжается до нахождения допустимой позиции, каждый раз фильтруя сетку карты, и не проверяет внутри себя `isGameplayActive` или наличие целей. Пауза 0,25 секунды уже есть, поэтому это не плотный цикл без ожидания. Но при отсутствии допустимой точки поиск может продолжать расходовать ресурсы без результата, в том числе после изменения фазы матча.

Кандидат: ограниченный пакет попыток, повторная проверка фазы/наличия игроков и определенный сценарий восстановления при пустом списке кандидатов. Не размещать ящик в случайной нулевой позиции только ради завершения цикла. Для обычных успешных поисков этот пункт менее важен, чем бот-логика и силовое поле.

Дальнейшие мелкие изменения стоит ранжировать по игровым замерам: главные частые вычисления уже перечислены. Для долгого матча из этого прохода наиболее полезно проверить рост `miniBossList` и реальное количество наземных предметов, а для устойчивости — повторные активации расходников.
