## Телепорт зомби — суммарно −16

В [bots_game_in_progress.opy](../src/game/bots_game_in_progress.opy) две стадии
отбора сохранённых spawn points можно заменить одной:

```python
teleportCandidateSpawnPointList = botSpawnPointList.filter(lambda x, i: distance(x, eventPlayer.botTeleportCenter) < BOT_MAX_TELEPORT_RANGE and botSpawnPointTimerList[i] < 15)
```

Старый первый фильтр выбирает точки по расстоянию, второй ищет каждую точку
в исходном списке через `botSpawnPointList.index(x)` и проверяет соответствующий таймер.
Новый i принадлежит **исходному** botSpawnPointList, а не промежуточному фильтру.
Поэтому нельзя просто заменить index(x) на индекс во втором старом фильтре.

Проверен контракт уникальности: botSpawnPointList и timer list инициализируются
пустыми в VARIABLE ASSIGNMENT; единственный append в `updateBotSpawnPoints()`
защищён `not ... in botSpawnPointList`. Там же синхронно добавляются waypoint и таймер.
`removeBotSpawnPoint()` синхронно удаляет соответствующие записи; отдельный
таймерный map сохраняет длину и порядок. Других писателей точек в src нет.
Таким образом, для допустимого состояния `botSpawnPointList.index(x) == i`.
Порядок кандидатов и распределение следующего `random.choice` сохраняются.

Это также устраняет повторный линейный поиск по исходному списку для каждой точки.
На уровне алгоритма фильтрация больше не содержит вложенного index-поиска.
При eager-вычислении And таймер может читаться и для далёких точек; реальное
ускорение или изменение Server Load не измерялось.

Следующая проверка:

```python
if botSpawnPointList != [] and teleportCandidateSpawnPointList != []:
```

сокращается до `if teleportCandidateSpawnPointList != []:`. Непустой результат
фильтра уже означает непустой исходный список. Между фильтрами и этим if нет
wait, асинхронного вызова или изменения списков. Явное сравнение с [] сохраняется.
Проверены 69 905 моделей списков длиной 0..4 с порогами расстояния 40 и таймера 15,
включая отсутствие кандидатов и сохранение порядка результатов.

В `enterExitTeleport()` проверка `elif eventPlayer.botTarget != null` следует
за `if eventPlayer.botTarget == null`. Заменить её на else: сравнения — точные
логические дополнения, не проверки truthiness. Когда первый if ложен, между ним
и вторым допуском нет действия, меняющего target, либо ожидания.
Действия запуска движения и NOOP остаются прежними.

Альтернативная проба одного фильтра с прежним index(x) экономит только 2 элемента.
Она включена в JSON для сравнения, но её экономию нельзя прибавлять к −5:
это два варианта одной и той же правки.

## Engineer — −2

В [enhancements.opy](../src/abilities/enhancements.opy) `ENGINEER ARMOR TRANSFER`
сразу записать `sorted(...)[0]` в существующий `scrapArmorGrantTarget` (tmp1)
и проверять `scrapArmorGrantTarget != null` вместо `scrapTransferCandidates != []`.
Убрать промежуточный массив в tmp0 и последующее присваивание его первого элемента.

Запрос остаётся тем же: живые союзники Team 1, исключение self, LOS surfaces,
та же дальность/угол и сортировка по прицелу. Пустой результат даёт 0/Null,
сопоставимый с прежней пустотой массива при этом типе содержимого.
Непустой массив состоит из валидных игроков.

Сохранить важную ветку: если выбранный союзник уже имеет 200 armor,
отказать с прежним сообщением и **не переходить к self**.
Self остаётся fallback только при отсутствии выбранного союзника и свободном капе.
Плата 35/70, выдача HP pool, эффекты и reevaluated beam не меняются.
tmp0 по-прежнему доступен для последующего `scrapArmorGrantCost`;
при внедрении удалить неиспользуемый alias кандидатов и обновить его комментарии.
Модель проверила 192 сочетания наличия союзника, armor cap и остатка scrap.

## Pregame — суммарно −14

В `PLAYER SELECTS/RESELECTS HERO` в [player_start_menu.opy](../src/game/player_start_menu.opy)
после прежнего ожидания и проверки isPregameSetup общий допуск можно выразить так:

```python
eventPlayer.augmentId == Augment.NO_PREFERENCE and eventPlayer.enhancementId == Enhancement.NO_PREFERENCE and (not isVoting or (not eventPlayer.pregameChallengeVote and not eventPlayer.pregameZombieVote and not eventPlayer.pregameObjectiveVote))
```

В исходном выражении `enhancementId == NO_PREFERENCE` повторяется в двух ветках.
При открытом голосовании по-прежнему требуются все три нулевых голоса, при закрытом
голосовании прежние голоса не препятствуют автоподтверждению. В обоих случаях
Enhancement и Augment должны быть NO_PREFERENCE. Проверены 1728 комбинаций
состояния голосования (включая unset 0), ID и значений голосов.
Само нажатие Jump, waits, camera lifecycle и native menu guards не переносятся.

В `PREVENT PLAYERS FROM LEAVING START EARLY` заменить горизонтальное расстояние на:

```python
magnitude((eventPlayer.getPosition() - eventPlayer.pregamePosition) * vect(1, 0, 1)) > 0.6
```

Порог 0,6 и допуски isPregameSetup/hasSpawned/pregameState не меняются.
Проверены 10 000 моделей конечных координат, включая границу и соседние значения.
Размещение игрока и точка крепления для special modes остаются прежними.
Это численная модель JavaScript, а не тест точности движка.
