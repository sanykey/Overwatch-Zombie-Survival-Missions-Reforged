### Born to Battle: исправлен пограничный случай предыдущей пробы

В [enhancements.opy](../src/abilities/enhancements.opy), правило
`BORN TO BATTLE PLAYER USES ABILITY CHARGE`, цепочку присваиваний по кнопкам заменить:

```python
eventPlayer.enhancementBattleAbilityButton = [Button.SECONDARY_FIRE, Button.ABILITY_1, Button.ABILITY_2, Button.CROUCH, Button.JUMP].filter(lambda button: eventPlayer.isHoldingButton(button)).concat(eventPlayer.enhancementBattleAbilityButton)[0]
```

Порядок кнопок повторяет исходные if/elif. Прежнее значение дописывается в конец
отфильтрованного массива: если между проверкой Conditions и Actions все кнопки
отпущены, значение сохраняется. У предыдущей отклонённой пробы этого fallback не было.

Скомпилированная форма — `First Of(Append To Array(Filtered Array(...), oldValue))`.
Состояние читается и записывается на том же игроке до существующих ожиданий;
проверки готовности и специальные ветки Reinhardt/Zarya/Reaper сохраняются.
Проверены 256 сочетаний удерживаемых кнопок и прежнего скалярного значения.
Контракт `actorTeamSlot23` рассмотрен: у Team 1 роли этого слота — скалярные
состояния/кнопки/ID, массив радиусов газа принадлежит Team 2. Этот вариант не следует
переносить на произвольное поле-массив: Append To Array с массивом разворачивает его.

Компромисс: фильтр проверяет пять кнопок и строит массив вместо раннего выхода
цепочки if/elif. Это происходит при активации сброса, без нового фонового цикла.
Уменьшение CPU не заявляется.

### Таблица имён мутаций

В `mutationsMacro()` в [subroutines.opy](../src/core/subroutines.opy) убрать пять
веточных `startForcingName` и вызвать один после изменения характеристик:

```python
eventPlayer.startForcingName(["SPEED", "XL", "XS", "Radioactive", "Heavy"][eventPlayer.botMutationId - 1])
```

`availableMutationList` создаётся в `enableMutationsMacro()` из ID 1..5;
`botMutationId` выбирается из этого массива. Все пять названий сопоставлены
исходным веткам. Цвета, характеристики, выбор случайной мутации и очистка имени
для немутировавших ботов остаются прежними. Вызов остаётся перед созданием outline.

Компилятор упаковывает таблицу в `String Split`; экономия измерена после упаковки.
Компромисс — разбор строки/индексация при инициализации мутанта вместо литерала
в выбранной ветке. Это экономия размера, без доказанного ускорения.

### Ещё одно переиспользование флага защиты

В `applyDamageReceivedModifier()` в [hero_tuning.opy](../src/abilities/hero_tuning.opy)
сначала вычислить существующие `isDotProtected` и `hasDamageResist`, затем:

```python
eventPlayer.setDamageReceived(0 if eventPlayer.augmentId == Augment.DASH and eventPlayer.augmentDashSmokeEntity != null else 50 if eventPlayer.hasDamageResist else 100)
```

Отдельная проверка Dash сохраняет его приоритет 0%; общий флаг даёт 50%
при Nano/ultimate, иначе 100%. Проверены восемь булевых сочетаний Dash/Nano/ultimate.
Нет ожиданий/асинхронных вызовов между присваиваниями и Set Damage Received.
Убирается повторное вычисление Nano/ultimate, но меняется порядок трёх действий:
две записи флагов теперь предшествуют Set Damage Received.
Статический анализ не показывает изменения итогового состояния; в игре требуется
проверить пересечения Dash, Nano, ultimate и смерти.
