## Турель: повторный поиск видимых целей

В `sentryTurret()` в [supply_drops.opy](../src/items/supply_drops.opy) каждая итерация
сначала проверяет наличие видимого нетелепортирующегося врага, затем снова
собирает видимых врагов для выбора цели по прицелу.

Предложение: сохранить `getLivingPlayers(Team.2).filter(lambda player:
isInLoS(eventPlayer.powerUpTurretPosition, player))` в существующий `tmp0`
под смысловым alias `turretVisibleTargets`, проверить `.any(lambda player:
not player.botIsTeleporting)` и передать тот же список в прежнюю сортировку.

Важно сохранить исходную особенность: признак teleporting участвует только в
допуске выстрела, а сортировка выбирает из **всех видимых** целей. Убирать
телепортирующихся из сохранённого списка означало бы менять поведение.
Не меняются LoS-аргументы, угол сортировки, стабильный порядок исходного списка,
рандомный разброс и дальнейшие raycast/damage.

Жизненный цикл tmp0: список → позиция попадания → поражённый игрок. Первое значение
потреблено при записи `powerUpTurretDirection`, до переиспользования слота.
Между записью списка и последним чтением нет wait, damage, вложенных вызовов или
захвата scratch в reevaluated эффекте. При отсутствии целей после проверки
список больше не читается. Общая пауза 0,125 секунды остаётся прежней.

Проверены 256 комбинаций visibility/teleporting четырёх кандидатов, включая
отсутствие доступной цели и одинаковые углы сортировки.
Это модель, не игровой тест. На итерациях с выстрелом устраняется повторный
поиск и повторная проверка LoS по тем же врагам. На итерациях без выстрела
создаётся временный массив; исходный any мог завершить поиск раньше.
Снижение Server Load не измерено, безусловное ускорение не заявляется.

Дополнительно −2 даёт вынесение общего `+ Vector.UP` из двух веток выбора
начальной позиции турели:

```python
eventPlayer.powerUpTurretPosition = (eventPlayer.getPosition() if eventPlayer.isOnGround() else nearestWalkablePosition(eventPlayer.getPosition())) + Vector.UP
```

Выбор между текущей и ближайшей проходимой позицией сохраняется, вертикальный
offset применяется один раз с теми же значениями и порядком сложения.

## Общие подпрограммы

- `playShowdownRing()`: неизменный Play Effect с оранжевым кольцом, текущей позицией
  задания и радиусом `objectiveRad * 2`. Потребители — завершение задания
  в `objectivesManagement()` и checkpoint в `INCREASE OBJECTIVE CAPTURE PERCENTAGE`.
  Тип эффекта, получатели, позиция в последовательности действий и звук не меняются.
- `advanceSpawnRoomIndex()`: ровно `spawnRoomIndex = (spawnRoomIndex + 1) % len(attackSpawnRooms)`.
  Потребители — Pregame rotation и gameplay control. Start Forcing Spawn остаётся
  у вызывающих правил, с их исходными Team.ALL/Team.2 и проверками безопасности.
- `shuffleBiowasteQueue()`: ровно `biomorphingQueuedTypeList = random.shuffle([0, 1, 2])`.
  Потребители — начало цели Biomorphing и пополнение исчерпанной очереди ресурсов.
  Перетасовка остаётся одной на вызов; список ID, количество и порядок случайных
  операций относительно остальных действий не меняются.
- `selectIndexedAbilityTarget()`: `eventPlayer.botAbilityTarget = eventPlayer.botSpecialTargetList[index]`.
  Потребители — Reaper Shadow Step, Emre Flight и Smolder Super Slam. Все три
  индекса (`shadowStepFloatTargetIndex`, `slimerFlightTargetIndex`,
  `smolderShockwaveTargetIndex`) объявлены alias одного `tmp0`.
  Подпрограмма только читает индекс и список того же Event Player, не меняет tmp0
  и не ждёт. При внедрении оформить вход helper через смысловой `#!define` alias
  и описать контракт около определения; не оставлять необъяснённое чтение tmp0.

Компромисс: подпрограммы добавляют Call Subroutine вместо раскрытого действия.
Особенно заметен путь выбора цели внутри частых циклов Reaper/Emre: экономия 8
элементов не является доказательством ускорения. Дополнительных циклов и
периодических проверок сами подпрограммы не создают.

## Горизонтальные дистанции

Showdown, правило `PLAYERS ON OBJECTIVE CONTROL`:

```python
magnitude((currentObjectivePosition - eventPlayer.getPosition()) * vect(1, 0, 1)) < objectiveRad
```

Rescue, правило `DELETE PATH`, внутри прежнего `.any(...)`:

```python
magnitude((rescueSurvivor.getPosition() - x) * vect(1, 0, 1)) < 0.25
```

Обе замены выражают ту же длину горизонтальной разности. Вертикальные ограничения
Showdown (`abs(...) < 12`) и Rescue (`abs(...) < 2`) сохраняются отдельно.
Индекс/выбор точки пути и обрезка пути не меняются. На 10 000 наборах конечных
координат, включая 0,25 и соседние значения, численная модель дала одинаковые длины.
Это JavaScript-модель, а не замер арифметики Workshop; проверить в игре вход/выход
из цилиндра Showdown и удаление пройденных точек на лестницах/склонах.
