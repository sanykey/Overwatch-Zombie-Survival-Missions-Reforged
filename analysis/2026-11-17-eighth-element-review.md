## Камера — −15

В `applyPlayerCamera()` в [player_camera.opy](../src/game/player_camera.opy) начало
луча `CAMERA_ORIGIN` повторяется трижды внутри двух вложенных raycast. Это одна
и та же формула с позицией игрока, eye distance и вертикальным смещением 0,5.
Её нельзя сохранять в scratch или замораживать через evalOnce: камера должна
продолжать двигаться за игроком.

Предложение — локальная область выражения через singleton map:

```python
[CAMERA_ORIGIN].map(lambda origin: raycastHitPosition(origin, raycastHitPosition(origin, origin + eventPlayer.getFacingDirection() * -3, null, eventPlayer, true), null, eventPlayer, true))[0]
```

Это замена только первого position-аргумента Start Camera. Второй аргумент
взгляда, коэффициент 100, оба вложенных луча и их include/exclude/true остаются
прежними. Ни alias CAMERA_ORIGIN, ни формула eye distance не упрощаются.
Вся конструкция остаётся выражением Start Camera и заново вычисляется при его
переоценке. Не добавлять evalOnce, отдельное присваивание позиции или chasing-cache.

Скомпилированный аргумент — `First Of(Mapped Array(Array(origin-expression),
Ray Cast Hit Position(Current Array Element, Ray Cast Hit Position(...))))`.
Автоматически проверены два Ray Cast Hit Position, один Mapped Array,
три обращения к Current Array Element и отсутствие Evaluate Once.

Модель на 10 000 наборах позиций/eye offsets/facing сравнила результаты и порядок
обоих вызовов детерминированной raycast-заглушки. Это проверка подстановки общего
выражения при одинаковых входах, **не тест реальных стен, камеры или движка**.
В игре нужны движение у стен, переключение режимов, zoom Ana/Ashe/Widowmaker/Emre,
смерть, возрождение и смена героя.

Компромисс: на каждую переоценку создаются массив длиной 1 и map вместо двух
повторных вычислений origin. Persistent variables, фоновых правил и новых сущностей
нет. Реальная скорость native map/raycast не измерялась; меньший elements не
является доказательством ускорения.

## Rescue — −9

В `INITIALIZE SURVIVOR TO BE RESCUED` в
[objective_type_survivor_rescue.opy](../src/objective_types/objective_type_survivor_rescue.opy)
направление движения сначала проверяет наличие точек пути ближе 2 м через any,
потом повторяет тот же поиск через filter, выбирая последнюю близкую точку.
При отсутствии точек направление ведёт к `rescueLeader`.

Вместо условного выражения можно использовать:

```python
[eventPlayer.rescueLeader].concat(eventPlayer.rescuePathList.filter(lambda x: distance(eventPlayer, x) < 2)).last()
```

Лидер помещён первым; за ним дописаны подходящие точки в прежнем порядке.
Последний элемент — прежняя последняя близкая точка либо лидер, если таких точек нет.
Обёртка `[leader]` намеренная: сохраняет сам fallback-элемент при добавлении массива.
Не заменять выбор проверкой truthiness: нулевой вектор является допустимой точкой пути.

В выражении Start Throttle сохраняются live reevaluation, радиус `< 2`, выбор
последней точки, speed-предикат, отсутствие лидера, величина скорости, направление
world и режим замены throttle. Путь, лидер и позиции не кешируются между кадрами.
Проверены 1022 модели путей длиной 0..8, всех сочетаний близких/далёких точек и
лидера 0/player, включая повторные и нулевые векторы в пути.

Компромисс: добавляются singleton fallback и concat, устраняется проход any
с повторным вычислением расстояний на успешной ветке. При отсутствии подходящих
точек исходный код не создавал filtered array; новый его создаёт. Поэтому
безусловное снижение CPU/аллокаций не утверждается.

двух полных f-строк с одинаковой привязкой Interact:

```python
f"{'Throw' if localPlayer.enhancementCarryState != WrestlerCarryState.NONE else 'Grab'}: [{inputBindingString(Button.INTERACT)}]"
```

Проверка carry state, порядок Throw/Grab, двоеточие, пробелы, скобки и динамическая
привязка остаются прежними. Внешняя строка с Pull-таймером и HUD reevaluation не меняется.
