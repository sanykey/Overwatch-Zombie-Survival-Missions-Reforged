При отсутствии видимых целей First Of пустого массива даёт отсутствие игрока (0/Null), которое отсекает существующий **явный** `botCandidateTarget != null`. Проверка не заменяется truthiness. Текущая цель и её история по-прежнему меняются только в прежних ветвях; `deselectBotTarget()` и Start Rule остаются на своих местах. Временное обнуление перед циклом больше не нужно: оно не имело других читателей между действиями. Удаляемый tmp0-индекс не используется после поиска; selectTarget запускается асинхронно, а не возвращает индекс вызывающему коду.

Проверены 2047 моделей списков длины 0..10 со всеми масками LoS. Сохранён выбор того же объекта либо отсутствие результата. Это модель неизменного снимка входов, а не тест нативного LoS и игрового планировщика.

**Существенный компромисс:** filter строит массив всех подходящих кандидатов, а исходный цикл прекращает LoS-проверки на первом подходящем. В моделях суммарно 4072 вызова предиката у исходного цикла против 18 434 у filter; это не репрезентативная игровая нагрузка и не замер CPU. При первой видимой цели в списке длины N количество LoS-проверок может вырасти с 1 до N. Вместе с тем исчезают Workshop-действия управления циклом; итоговую стоимость нативной фильтрации и LoS без Server Load-профиля установить нельзя.

Для проекта с приоритетом elements этот вариант даёт самый большой выигрыш данного набора. Для приоритета частоты/стоимости LoS использовать скомпилированный вариант −8 и сохранить цикл. При внедрении полного набора нужны сравнение Server Load при полном составе ботов и проверка переключения целей за стенами, невидимости, dummy/rescue, miniboss-приоритетов, пустого списка и смерти текущей цели.

## Living Projectile: один owner внутри Condition — −6

В `abilities/enhancements.opy` меняется только второе Condition правила `LIVING PROJECTILE RELEASE`:

```python
# Было
@Condition (eventPlayer.wrestlerZombieCarrier.enhancementCarryState == WrestlerCarryState.THROW_REQUESTED or not livingProjectileValid(eventPlayer.wrestlerZombieCarrier)) == true
# Предлагается
@Condition [eventPlayer.wrestlerZombieCarrier].any(lambda carrier: carrier.enhancementCarryState == WrestlerCarryState.THROW_REQUESTED or not livingProjectileValid(carrier)) == true
```

Carrier остаётся live-значением условия и заново читается при reevaluation; evalOnce и сохранение в переменную не добавляются. Первое отдельное Condition `eventPlayer.wrestlerZombieCarrier != null` сохраняется. Все проверки внутри livingProjectileValid, приоритет THROW_REQUESTED и тело Actions остаются прежними.

В экспорте получается внешнее `Is True For Any(Array(owner), ...)`, а существующее `Is True For All(Array(validity flags), Current Array Element)` остаётся вложенным. Owner-ссылки находятся в аргументе построения внутреннего Array и относятся к внешнему Current Array Element; внутренний Current Array Element в предикате All уже означает очередной boolean-флаг. Проверены ожидаемая вложенная структура и семь ссылок Current Array Element в Conditions. Макрос livingProjectileValid и его второе раскрытие в Actions не меняются.

6144 модели проверили все сочетания одиннадцати validity-флагов и трёх состояний carry. Модель не эмулирует нативные player references, вложенные массивы Workshop или отключение носителя. Игровые проверки: отпускание по таймеру, повторное нажатие для броска, смерть/CC/смена героя носителя, disconnect, смерть и телепортация переносимого бота, кредит урона после задержки. Проверить и освобождение без броска, и бросок.

Компромисс: каждый пересчёт Condition создаёт singleton array и выполняет Any вместо повторных чтений поля носителя. Меньшее число элементов не доказывает ускорение. Новых фоновых правил или scratch нет.

Это изменение выражения Condition, поэтому нельзя описывать весь набор как побуквенно неизменные Conditions. Сохраняются их число, отдельный owner guard и логика проверки, а также все Actions данного правила. `uiPhaseAndId` и событийные guards не меняются.
