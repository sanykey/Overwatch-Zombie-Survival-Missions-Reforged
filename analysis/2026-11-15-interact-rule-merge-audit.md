# Объединение обработчиков Interact

Аудит выполнен без изменения игровых исходников и main.ws.txt. Эксперименты компилируются в памяти скриптом `2026-11-15-interact-rule-merge-audit.cjs`; результаты — в `2026-11-15-interact-rule-merge-results.json`.

## Текущая структура

Четыре отдельных Ongoing Each Player обработчика: выбор аугмента в меню, основной PLAYER INTERACT (предметы и WRESTLER), APOTHECARY TELEPORT, LASER BARRICADE (PLACEMENT). Проверка отмены Cloaking Device находится внутри уже работающей подпрограммы; перенос этой проверки сам по себе не удаляет отдельное правило ввода.

Все три компиляции OverPy 9.7.21 завершились без предупреждений. Это измерение размера, а не скорости, памяти или исправности UI. Скомпилированные варианты не проверены в игре и не являются готовыми исправлениями.

У объединённого Crouch-обработчика сохранены общие ограничения и развёрнутое условие готовности одной из двух абилок, затем выполняется соответствующая ветка. Для Апотекария добавлена явная проверка augmentId, чтобы общий алиас augmentState1 не интерпретировался как его готовность у других аугментов. Разделяемая переменная для баррикады содержит вектор. Источники и срок жизни алиасов нельзя игнорировать при объединении. Равнозначность переходов условий при смене аугмента/фазы внутри ожиданий требует отдельной проверки.

## Почему не стоит просто разделять Interact и Interact без Crouch

Два взаимно исключающих условия не означают два независимых нажатия. Последовательность Interact → Crouch → отпустить Crouch, сохраняя Interact, снова делает истинным условие Interact без Crouch. Такой обработчик может использовать powerup после отменившего его приседания. Для строгого сохранения текущего поведения потребуется блокировка до отпускания Interact — через состояние или ожидание. Само нажатие Interact также может повторно выполнить подбор, если перенести его в оба правила.

При этом начало удержания Crouch после Interact должно запускать телепорт или подготовку баррикады. Один диспетчер, который только раз проверяет Crouch в момент нажатия Interact, пропустит этот переход. Нужны наблюдение за переходами/ожидание либо отдельный обработчик сочетания.

Нельзя последовательно выполнять предметы, телепорт и всю баррикаду в одном потоке: баррикада ждёт отпускания кнопки и затем отсчитывает перезарядку; это заблокирует новые предметные взаимодействия в том же правиле. Асинхронная подпрограмма убирает блокировку, но не сокращает само наличие подпрограммы и требует защиты от повторного запуска.

## Рекомендация

Не делать два взаимно исключающих правила. Если сокращение Each Player обработчиков важнее нескольких дополнительных элементов, рассмотреть два игровых обработчика: основной Interact для предметов/WRESTLER с сохранением подбора при Crouch; общий Crouch+Interact для абилок. Меню пока оставить отдельным. Это сокращает игровые обработчики с трёх до двух, а все четыре обработчика ввода — до трёх. Компиляционный прототип даёт +3 элемента, поэтому по первому приоритету проекта он пока не выгоднее текущей реализации.

Всего в сборке 153 Each Player правила; объединение ввода затрагивает небольшую их часть. Большое число таких правил само по себе не доказывает причину поломки UI. Для диагностики сравнить Server Load/Peak/Average при одинаковом числе игроков/ботов, а также число созданных HUD, текстов и эффектов и их переоценку. Отдельный кандидат из текущего кода: createBeam предпросмотра баррикады в src/player_initialization.opy содержит raycast в выражении видимости и в обоих концах луча с включённой переоценкой. Это повод измерить нагрузку, а не утверждение о найденной причине сбоя.

Документация Blizzard описывает отдельный экземпляр Ongoing Each Player для каждого игрока, повторный запуск при переходе условий false→true и независимое выполнение экземпляров: https://news.blizzard.com/en-us/article/22938941/introducing-the-overwatch-workshop
